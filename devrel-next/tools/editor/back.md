## 에필로그

1장을 열 때 우리 손에 있던 것은 작별 편지 몇 통과 설문 숫자 몇 개였다. 그 여정은 10장에서 한 번 정리했다. 여기서는 이 책이 끝내 답하지 못한 질문들을 적어두려 한다. 책을 덮은 뒤에도 들고 다닐 만한 질문들이다.

## 답하지 못한 질문들

첫째, 에이전트를 위한 일은 제품의 성장으로 이어지는가. 4장 끝에서 본 xena의 댓글은 이 책의 모든 에이전트 이야기 위에 물음표를 남겼다. 에이전트가 문서를 읽는다는 증거는 늘고 있다. 그 독해가 채택과 매출로 이어진다는 공개 자료는 2026년 9월 시점에 찾지 못했다. 누군가 이 연결을 보여준다면 4장과 5장은 다시 쓰여야 할지도 모른다.

둘째, DevRel식 확산은 사내에서 정말 더 잘 작동하는가. 8장과 9장은 그 주장이 이론과 몇 개의 공개 사례에 기댄 것임을 스스로 밝혔다. 커뮤니티형 확산과 의무화를 견준 비교 연구는 없었다. 이 질문의 답은 어느 회사가 남긴 기록에서 먼저 나올지도 모른다.

셋째, 한국의 DevRel은 지금 어떤 모습인가. 7장은 공개 자료로 확인되는 장면 셋만 옮길 수 있었다. 국내 DevRel 인력의 규모도, 채용의 흐름도 공개된 숫자가 없었다. 이 공백은 이 책의 한계이기도 하고, 국내 DevRel 커뮤니티가 스스로 기록을 남길 이유이기도 하다.

넷째, '만든 증거'는 평가의 언어가 될 수 있을까. 5장과 9장에서 무엇이 달라졌는가를 세자고 했다. 그 제안이 한 사람의 보고서를 넘어 조직의 평가 기준으로 들어갈 수 있을지는 아직 모른다. 1장에서 본 측정의 난제는 이 책이 끝나는 자리에서도 풀리지 않은 채 남아 있다.

다섯째, 넓어진 'D'는 어디까지 넓어질까. 3장과 10장에서 본 상한론, 곧 메이커 운동처럼 참여자가 늘어도 결국 소수에 머물 수 있다는 반론은 가볍게 넘길 수 없다. 무언가를 만들 수 있게 된 사람이 늘어나는 것과, 그 사람들이 계속 만드는 것은 다른 이야기일 수 있다.

## 이 책을 읽는 법에 대한 마지막 당부

이 책은 2026년 9월의 스냅샷이다. 공고는 하루치 목록이었고, 수치는 대부분 벤더와 당사자가 내놓은 것이었으며, 연구의 상당수는 동료 검토 전 논문이었다. 그래서 이 책의 문장들에는 유통기한이 있다. 10장에 적은 관찰 지표들은 그 유통기한을 스스로 확인하라고 남겨둔 도구다. 1년 뒤 같은 공고 목록을 다시 열어보고, 같은 설문의 다음 판을 찾아보자. 이 책의 전망이 틀렸다면 그 사실도 그 자리에서 드러날 것이다.

더 깊이 읽고 싶다면 이 책이 기대어 선 책 세 권을 권한다. Mary Thengvall의 『기업의 성공을 이끄는 Developer Relations』(조은옥 옮김, 한빛미디어, 2022)는 DevRel의 가치를 조직 안에서 설명하는 법을 다룬다. Caroline Lewko와 James Parton의 『Developer Relations』(Apress, 2021)는 개발자의 여정을 단계별로 설계하는 틀을 준다. Everett Rogers의 『Diffusion of Innovations』(5판, Free Press, 2003)는 8·9장에서 빌려 쓴 확산 이론의 원전이다.

## 책을 덮으며 해볼 한 가지

2장에서 작은 연습을 했다. 회사의 DevRel이 하는 일을 한 문장으로 적고, 목적어와 동사에 밑줄을 긋는 연습이었다. 책을 덮으며 그 연습을 한 번 더 해보자. 이번에는 당신이 이번 주에 한 일 가운데 하나를 골라 한 문장으로 적는다. 그 일이 누구를 향했고 무엇으로 닿았는지가 드러나게. 그리고 그 문장을 다른 부서의 동료 한 사람에게 보여주고, 그 사람이 이해한 대로 자기 말로 다시 설명해달라고 부탁하자. 돌아온 설명이 당신이 적은 문장과 얼마나 다른지 들어보고 그 간격을 좁히는 것, 그것이 이 책 내내 따라온 일의 가장 작은 단위다.

# 부록 A. DevRel 직무 진단 워크시트

7장의 네 가지 기능(번역·피드백 루프·신뢰·먼저 가보기)과 3·4장과 8장에서 본 네 청중(전문 개발자·빌더·에이전트·회사 안의 동료)을 교차해 자기 업무를 기록하는 워크시트다. 현직 DevRel은 A-1~A-3을, 리더는 A-4를 먼저 쓰자.

## A-1. 지난 석 달의 업무 배분

캘린더, 이슈 트래커, 산출물 목록을 펴놓고 지난 석 달 동안 쓴 시간을 칸마다 대략의 비율로 적는다. 전체 합이 100이 되게 적자.

| 기능 \ 청중 | 전문 개발자 | 빌더(스스로를 개발자라 부르지 않는 사람) | 에이전트 | 회사 안의 동료 |
|---|---|---|---|---|
| 번역 — 한쪽의 언어를 다른 쪽으로 옮긴다 | | | | |
| 피드백 루프 — 들은 것을 되돌리고 바뀐 것을 다시 알린다 | | | | |
| 신뢰 — 만든 것으로 믿을 만한 사람이 된다 | | | | |
| 먼저 가보기 — 출시 전에 먼저 써보고 넘어진다 | | | | |

다 적었다면 세 가지를 살펴보자.

- 가장 큰 칸은 어디인가? 그 칸이 지금 당신의 자리다.
- 가장 작은 행은 무엇인가? 7장에서 봤듯 먼저 가보기가 비어 있다면 다른 세 기능의 재료도 곧 마른다.
- 에이전트 열과 동료 열이 비어 있는가? 비어 있다면 4장과 8장이 말한 새 청중을 아직 만나지 않은 것이다. 그것이 선택인지, 미뤄둔 일인지 적어두자.

## A-2. 기능별 증빙

기능마다 가장 좋은 증거 하나를 적는다. 6장에서 본 공고들은 결과물의 링크를 요구했다. 링크를 붙일 수 없다면 그 칸이 약한 칸이다.

| 기능 | 증거 한 줄 | 링크·위치 | 그 덕분에 달라진 것 |
|---|---|---|---|
| 번역 | 무엇을 누구의 언어로 옮겼나 | | |
| 피드백 루프 | 어떤 목소리를 제품에 전했고 무엇이 바뀌었나 | | |
| 신뢰 | 무엇을 만들어 가르쳤나 | | |
| 먼저 가보기 | 출시 전에 무엇을 먼저 써보고 무엇을 고치게 했나 | | |

## A-3. 인접 직함 찾기

A-1에서 가장 굵은 행을 골라, 그 기능을 가장 많이 쓰는 자리를 찾아보자. 7장의 목적지 목록을 기준으로 정리했다. 공고 예시는 2026년 9월 25일 공개 목록에서 가져온 것이고, 이후 바뀔 수 있다.

| 가장 굵은 기능 | 많이 쓰는 자리(7장) | 6장에서 이 동사가 보인 공고 |
|---|---|---|
| 번역·피드백 루프 | FDE, 솔루션 엔지니어 | Anthropic FDE("contribute insights back ..."), Anthropic Developer Relations("translating developer feedback ...") |
| 먼저 가보기 | 제품 엔지니어, Staff Engineer, MTS | Vercel DevRel Engineer("hit the rough edges first") |
| 신뢰·번역 | 교육 직무 | Vercel 지원 조건("something you made that taught developers something") |
| 네 기능 모두 | 사내 AX | 8장의 Block·카카오 공개 사례 |

찾았다면 이력서의 한 줄을 기능의 동사로 다시 써보자. 형식은 이렇다.

```text
[기능 동사] + [누구에게] + [만든 증거]
예) 출시 전 신규 API를 먼저 써보고(먼저 가보기) 발견한 문제 목록을 제품 팀에 전해 고치게 했다(피드백 루프).
```

## A-4. 리더용 판단 질문

7장 끝의 세 질문을 적어두고, DevRel 담당자와 함께 답을 맞춰보자.

1. **어느 기능이 병목인가?** 개발자가 문서를 이해하지 못하는가(번역), 커뮤니티의 불만이 제품에 닿지 않는가(피드백 루프), 개발자가 우리 주장을 믿지 않는가(신뢰), 출시 뒤에야 거친 부분이 드러나는가(먼저 가보기).
   - 우리 답:
2. **그 기능은 어느 조직에 붙어야 하나?** 먼저 가보기라면 제품 조직의 출시 일정 안에, 번역이라면 문서·교육 쪽에, 피드백 루프라면 제품 관리 쪽에 닿아 있어야 한다.
   - 우리 답:
3. **무엇을 '만든 증거'로 볼 것인가?** 그 일이 없었다면 없었을 결과 하나를 미리 정한다. 배포된 앱, 성공한 API 호출, 고쳐진 버그, 줄어든 지원 문의 같은 것들이다.
   - 우리 답:

마지막으로 한 줄을 더 적자. **이 기대를 당사자에게 말한 적이 있는가?** 없다면 이 워크시트를 함께 읽는 자리가 첫 대화가 된다.

# 부록 B. 에이전트 친화 문서 체크리스트

4장의 원리를 점검 항목으로 옮겼다. 근거가 연구인 항목과 실무 관행인 항목을 괄호로 구분했다. 인용한 연구 다수는 동료 검토 전 논문(프리프린트)이다. 관행은 빠르게 바뀌니 도입 전에 공식 문서를 함께 확인하자.

## B-1. 무엇을 적을까

- [ ] **모델이 모르는 것부터 적었는가.** 그 제품만의 비표준 규칙, 최신 API, 폐기된 API를 먼저 적는다. 컨텍스트 파일이 효과를 낸 것은 비표준 관행을 적었을 때였다(Gloaguen 등, 프리프린트).
- [ ] **폐기된 방식을 명시적으로 막았는가.** 모델의 학습 자료에는 옛 예제가 남아 있다. "이것 대신 저것을 쓰라"는 지시문 한 줄이 그 기억을 교정한다(Stripe llms.txt 지시문, 2차 인용).
- [ ] **저장소 개요를 반복하지 않았는가.** 개요 위주의 컨텍스트 파일은 성공률을 높이지 못하고 추론 비용만 늘렸다(Gloaguen 등, 프리프린트).
- [ ] **도구 설명에 목적과 인자를 분명히 적었는가.** MCP 도구 설명의 56%는 목적조차 밝히지 않았다. 모델은 이 설명을 보고 도구와 인자를 고른다(Hasan 등, 프리프린트).
- [ ] **길게 쓰는 것과 잘 쓰는 것을 구분했는가.** 설명을 보강하면 성공률은 조금 오르지만 실행 단계가 크게 늘 수 있다(Hasan 등, 프리프린트).

## B-2. 어떻게 건넬까

- [ ] **같은 내용을 마크다운으로 받을 수 있는가.** 페이지 주소에 `.md`를 붙이거나 `Accept: text/markdown` 요청에 마크다운을 돌려주는 방식이다(Stripe 사례, 커뮤니티 관행).
- [ ] **llms.txt를 두었다면 기대치를 조정했는가.** 2026년 9월 시점에 llms.txt는 제안이다. 검색 가시성 신호로서의 효과에는 회의적인 증언이 많다. 코딩 에이전트가 문서를 직접 가져가는 맥락과 구분해서 판단하자.
- [ ] **MCP 서버가 필요한 맥락인가.** 방대한 문서를 에이전트가 필요한 만큼만 가져가야 하거나, 개발자가 아닌 사용자가 업무 도구를 AI에 연결하려는 경우에 특히 쓸모가 있다(커뮤니티 의견).
- [ ] **에이전트가 찾을 수 있는 목록이 있는가.** 스킬이나 도구를 기계가 읽을 수 있는 카탈로그로 공개했는가(Stripe `/.well-known/skills/index.json` 사례).

## B-3. 보안과 유지보수

- [ ] **보안 요구를 적었는가.** 분석된 컨텍스트 파일 가운데 보안 요구를 명시한 것은 14.8%였다(Chatlatanagulchai 등, 프리프린트).
- [ ] **MCP 서버를 점검했는가.** 오픈소스 MCP 서버의 일부에서 일반 취약점과 도구 오염(tool poisoning)이 발견됐다(Hasan 등, 프리프린트). 공개 전에 점검 절차를 두자.
- [ ] **스킬과 지시문을 제품처럼 다루는가.** 버전을 붙이고, 변경 이력을 남기고, 제품이 바뀔 때 함께 고친다. "a skill is a living product, not a one-off document"(Google Cloud 블로그).

## B-4. 측정

- [ ] **자기 로그부터 열어봤는가.** 선언된 AI 클라이언트 이름과 기계 판독용 경로(`.md`, llms.txt 등)로 들어온 요청을 따로 모은다. 정체를 밝히지 않는 에이전트는 잡히지 않으니 하한으로 읽는다.
- [ ] **벤더 수치를 인용할 때 단위를 적었는가.** 에이전트 '요청'과 사람 '페이지 로드'는 다른 단위다(4장의 Mintlify 보고서).
- [ ] **분기마다 모델에게 직접 물어봤는가.** 실제 고객의 질문으로 여러 모델에 물어보고 답을 기록한다. LLM이라는 표면에서 무엇이 먹히는지 재는 방법은 아직 "largely unsolved" 상태다(5장의 Karlsson).

## B-5. 마지막 점검

- [ ] **이 체크리스트의 만점이 성장을 약속하지 않는다는 점을 팀과 공유했는가.** 4장 끝에서 본 xena의 댓글을 기억하자. 에이전트가 읽기 좋은 문서가 그것만으로 성장을 만든다는 증거는 2026년 9월 시점에 아직 없다.

# 부록 C. 사내 AI 확산(AX) 설계 캔버스

8·9장의 내용을 한 장짜리 캔버스로 옮겼다. 산문 설명은 본문에 있으니 여기서는 표와 빈칸만 둔다. 이 캔버스는 효과가 검증된 처방이 아니고, 설계 선택지를 정리하는 도구다(9장 첫 절의 한계 참조).

## C-1. Rogers 5속성 대응표

| 속성(Rogers) | 스스로에게 던질 질문 | 장치 예시(9장) | 우리 조직의 장치 |
|---|---|---|---|
| 상대적 이점 | 지금 방식보다 무엇이 나은가 | 부서별 사용 사례, 전후를 보여주는 사례 공유 | |
| 적합성 | 지금 쓰는 도구·데이터·일하는 방식에 맞는가 | 기존 사내 도구와 데이터 연결, MCP 서버 | |
| 복잡성 | 이해하고 쓰기 어려운가 | MVK(최소 필수 지식) 목록, 예제 프롬프트, 템플릿 | |
| 시험 가능성 | 작게 먼저 써볼 수 있는가 | 샌드박스, 파일럿, 한 시간짜리 행사 | |
| 관찰 가능성 | 다른 사람이 쓰는 결과를 볼 수 있는가 | 쇼케이스, 공유 채널, 실패 사례를 함께 보여주기 | |

## C-2. 세 다이얼

각 다이얼에서 지금 위치와 가고 싶은 위치를 표시하고, 그 이유를 한 줄로 적는다.

| 다이얼 | 한쪽 끝 | 다른 쪽 끝 | 지금 위치 | 목표 위치 | 이유 |
|---|---|---|---|---|---|
| 강도 | 권유 | 성과평가·채용 기준 반영 | | | |
| 측정 | 사용량(로그인·토큰) | 만든 증거와 그로 인해 달라진 것 | | | |
| 공유 장치 | 없음 | 업무 영역별 채널, 사례 큐레이션, 이름 표시, 실패 사례 포함 | | | |

세 다이얼은 따로 움직이지 않는다. 강도를 올리면 측정이 따라 올라가기 쉽고, 측정이 사용량에 머물면 감시로 읽히기 쉽다. 강도를 올릴 계획이라면 공유 장치부터 갖추자.

## C-4. 허영 지표 경고 목록

다음 신호가 보이면 측정 다이얼을 다시 보자.

- 토큰 사용량이나 AI 생성 코드 줄 수로 순위를 매기는 리더보드가 생겼다.
- 로그인 수, 행사 참석자 수, 채널 가입자 수가 보고서의 첫 줄에 올라 있다.
- 사용량 지표가 개인 평가와 바로 이어져 있다.
- 사람들이 쓰는 척하기 시작했다는 이야기가 들린다.
- 숫자가 들어간 분석, 외부로 나가는 문서, 운영 환경에 닿는 코드에 사람의 확인 단계가 없다.
- 도구가 없어지면 곤란하다는 응답이 늘었는데, 도구 없이 설명하거나 검증할 수 있는 사람은 늘지 않았다. 역량이 자란 것인지 의존이 생긴 것인지 물어보자(9장의 '원숭이 꽃신').

# 부록 D. 용어집

- **DevRel(Developer Relations)** — 플랫폼 바깥의 개발자와 관계를 맺는 일. 이 책은 누구에게(D)와 무엇으로(R) 두 변수로 이루어진 경계 역할로 읽는다(2장).
- **Developer Advocate** — 회사의 메시지를 개발자에게 전하는 동시에 개발자의 목소리를 회사 안에 전하는 직무. 에반젤리스트의 설득에 양방향 피드백이 더해진 이름이다(2장).
- **에반젤리스트(evangelist)** — 1984년 매킨토시 시절 Apple의 "software evangelist"로 널리 알려진 직함. 서드파티 개발자가 플랫폼에서 무언가를 만들도록 설득하는 일(2장).
- **경계 역할(boundary role)** — 조직 바깥의 정보를 안으로 들여와 번역하고 퍼뜨리는 역할. Tushman(1977)의 개념을 빌렸다(2·8장).
- **DX(Developer Experience, 개발자 경험)** — 개발자가 일하는 환경 안에서 자기 활동을 어떻게 생각하고 느끼는지를 포착하는 개념(Fagerholm & Münch, 2012). DevEx는 피드백 루프·인지 부하·몰입을 다룬 실무자 대상 기고의 틀이다(2장).
- **AX(Agent Experience)** — AI 에이전트가 제품이나 플랫폼의 사용자로서 겪는 경험 전체. Mathias Biilmann이 2025년 1월 제안했다(4장).
- **AX(AI Transformation)** — 조직에 AI를 들여 일하는 방식을 바꾸는 일. 저자가 하는 일이며 PART 4의 주제다. 두 AX가 같은 약어를 쓰는 것은 우연의 일치다(8장).
- **ACI(Agent-Computer Interface)** — 언어 모델 에이전트를 새로운 범주의 최종 사용자로 보고, 에이전트가 쓰는 인터페이스를 따로 설계하자는 개념. SWE-agent 논문에서 나왔다(4장).
- **MCP(Model Context Protocol)** — AI 어시스턴트를 데이터와 도구가 있는 시스템에 연결하는 프로토콜. Anthropic이 2024년 11월 발표했고, 2025년 12월 Agentic AI Foundation의 창립 프로젝트가 됐다(4장).
- **llms.txt** — 웹사이트 루트에 두어 에이전트에게 사이트 사용 정보를 건네자는 마크다운 파일 제안(2024년 9월). 2026년 9월 시점에도 제안 단계다(4장).
- **AGENTS.md** — 저장소 수준에서 코딩 에이전트에게 맥락과 지시를 건네는 컨텍스트 파일. Agentic AI Foundation의 창립 프로젝트 가운데 하나다(4장).
- **스킬(Agent Skills)** — 에이전트가 특정 작업을 수행하도록 묶은 지시와 자원. 한 번 쓰고 끝나는 문서로 두지 않고 계속 고쳐야 하는 제품처럼 다루자는 것이 4장에서 본 교훈이다.
- **FDE(Forward Deployed Engineer)** — 전략 고객 곁에 붙어 제품을 실제 업무에 들이고, 거기서 배운 것을 제품 팀에 되돌리는 엔지니어(6장).
- **바이브 코딩(vibe coding)** — 자연어로 지시한 AI로 코드를 쓰는 일. Andrej Karpathy가 2025년 2월 이름을 붙였고, Collins 사전이 2025년 올해의 단어로 골랐다(3장).
- **최종 사용자 프로그래밍(end-user programming)** — 전문 개발자가 아닌 사람이 자기 본업의 목표를 위해 프로그램을 쓰는 일. 엑셀 수식이 대표적인 예다(3장).
- **빌더(builder)** — 이 책에서는 스스로를 개발자라 부르지 않으면서 소프트웨어를 만드는 사람까지 포함해, 무언가를 만드는 사람을 넓게 부르는 말(3장).
- **만든 증거** — DevRel이나 사내 확산 활동이 있었기 때문에 실제로 달라진 것(배포된 앱, 성공한 호출, 동료가 가져다 쓴 템플릿 등). 활동량 지표와 구분하려고 이 책이 붙인 이름이다(5·9장).
- **프리프린트(preprint)** — 동료 검토를 거치기 전에 공개된 논문. 이 책은 인용할 때마다 이 사실을 밝혔다.
